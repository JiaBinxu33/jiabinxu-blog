          # 需求功能点澄清

          # 概述

          通过协助性提问，帮助开发工程师澄清需求的核心功能点，明确边界，结合代码理解分析影响范围，最终输出清晰的 DRAFT_SPEC.md 文档。

          Announce at start: "我正在使用 wmb-clarifying-requirements skill 协助你澄清需求点"

          # 术语定义（重要）

          术语 定义 粒度 正确示例 错误示例
          功能点 产品维度的独立模块，能独立向用户交付价值 一个功能点 = 一个 feature 文件 "通用汇总卡片组件"、"用户登录"、"towxml链接点击埋点" "添加导入"、"修改方法"、"卡片基础结构"
          实现步骤 功能点内的技术任务（在后续设计阶段拆解） 多个步骤组成一个功能点 "创建组件结构"、"实现数据展示"、"添加埋点逻辑" -

          功能点判断标准：

          • ✅ 能独立向产品/用户交付价值
          • ✅ 可以独立测试和验收
          • ✅ 对应一个完整的业务场景
          • ❌ 仅是技术实现的中间环节
          • ❌ 无法独立使用，必须依赖其他部分才有意义

          ⚠️ 常见错误：把一个组件/模块的不同方面拆成多个功能点。如果多个"功能点"描述的是同一个东西的不同侧面（如"卡片基础结构"、"指标数据展示"、"布局自适应"都是同一个卡片组件的方面），它们应该合并为一个功能点。

          # 澄清流程

          # 1. 创建规格文档

          • 必须使用 cp 命令复制 DRAFT_SPEC_template.md 模板创建规格文档
          • 分段展示文档内容，根据反馈调整和完善

          # 2. 收集需求信息

          • 让开发人员提供需求背景信息
          • 收集具体的需求点描述
          • Focus on understanding: purpose, constraints, success criteria

          # 3. 理解项目现状和关联性

          • 强制通过子Agent探索代码仓库了解现有系统结构
          • 检查当前项目状态（文件、文档）
          • 识别需求点与现有业务模块的关系
          • 分析可能受影响的技术组件

          # 4. 按功能点逐一澄清

          • 参考 clarification_guide.md 中的提问思路，协助开发澄清每个功能点
          • 结合代码理解，有针对性地提问和确认，一次只问一个问题
          • 每个问题必须可通过以下方式回答：
            • 简短多选题（2–5 个互斥选项），或
            • 单词/短短语答案（明确限制：“答案不超过 5 个单词”）；
          • 直到你有95%的信心理解理解某个功能点后，完成总结，用户确认后马上将其填入规格文档中，不要等到全部澄清后再填入。
          • 分段展示（200-300字），每段后询问是否准确
          • 涵盖：功能边界、数据流程、交互方式
          • 保持灵活，根据反馈调整理解

          # 5. 整合和生成规格文档

          • 将所有澄清的功能点整合
          • 确认功能点之间的依赖关系

          # 完成后的行动

          文档化

          • 将验证的需求规格写入 docs/design/YYYY-MM-DD-<需求名称>/DRAFT.md
          • 提交文档到 git：git add . && git commit -m "docs: 新增<需求名称>需求点澄清文档"

          下一步 (如果用户继续):

          • 询问："准备好技术方案设计了吗？"
          • 使用 wmb-technical-design 进行技术方案&实现方案设计

          # 核心原则

          • 一次一个问题 - 不要用多个问题压倒用户，如果需要深入探索，将复杂问题分解为多个简单问题
          • 多选优于开放 - 尽可能提供选择题而非开放式问题，降低回答难度
          • YAGNI 原则 - 无情地识别和排除不必要的功能，专注核心需求
          • 增量验证 - 分段展示功能点和文档内容（200-300字），每段后询问是否准确再继续
          • 绝对复制 - 规格文档创建只能使用 cp 命令复制模板，不可直接编写
          • 无代码 - 不可以在文档中出现大量的代码，可以出现少量仅用于协助理解（不得超过5行），仅在必要的时候引用文件
          • Be flexible - Go back and clarify when something doesn't make sense
