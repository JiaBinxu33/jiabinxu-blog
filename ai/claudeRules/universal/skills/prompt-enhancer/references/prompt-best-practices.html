        # 提示词最佳实践知识库

        # 一、高质量提示词的六个要素

        要素 说明 缺失时的后果
        角色 Claude 应以什么身份执行任务 输出风格和专业度偏差
        任务 具体要做什么，动词明确 执行方向跑偏
        上下文 背景信息、技术栈、约束条件 输出无法落地，缺乏针对性
        输入 提供什么材料或数据 Claude 靠猜测补全
        输出格式 期望的结果形式 需要反复追问才能得到想要的格式
        约束 禁止做什么、必须遵守什么 输出质量不可控

        并非每个任务都需要六个要素齐全，但任务 + 上下文 + 输出格式是最低标准。

        # 二、常见弱提示词 → 强提示词对比

        # 场景：迁移页面

        # 弱
帮我迁移这个页面

# 强
你是一名 Flutter → React 迁移工程师。
将 [Flutter文件路径] 迁移为 React 实现。

要求：
- 以 Flutter 源码为唯一 UI/逻辑权威参考
- 使用 @roo/roo-b-mobile 组件库（H5 端）
- 金额格式化使用 formatMoney()，时间格式化使用 formatYYYYMMDD()
- 迁移完成后运行 pnpm run check，修复所有报错

输出：完整的 React 组件代码 + index.module.scss

        # 场景：Code Review

        # 弱
帮我看看这段代码

# 强
Review 以下代码，重点检查：
1. TypeScript 类型安全（禁止 any）
2. 空值处理（接口数据是否有 ?? 兜底）
3. 命名规范（变量/函数/组件是否符合驼峰规范）

输出：按严重程度分级（🚫 必须修复 / ⚠️ 建议修复），每条附行号和修改建议

        # 场景：写组件

        # 弱
写一个列表组件

# 强
用 React + TypeScript 写一个订单列表组件。

技术约束：
- 组件库：@roo/roo-b-mobile（H5 端）
- 样式：index.module.scss（禁止 inline style）
- 禁止 any 类型
- 单文件不超过 200 行

数据结构：[粘贴接口返回的数据结构]

需要支持：空状态展示、加载中 skeleton、列表项点击跳转

输出：index.tsx + index.module.scss 完整代码

        # 三、上下文提供技巧

        # 技术栈上下文模板

        技术栈：React 18 + TypeScript + SCSS
组件库：@roo/roo-b-mobile（H5）/ @roo/roo（PC）
代码规范：ESLint + TypeScript strict mode
包管理：pnpm

        # 约束条件写法

        # 用「禁止/必须」而非「最好/建议」
禁止：any 类型、== 比较、内联样式、gap CSS 属性
必须：=== 比较、formatMoney() 金额格式化、pnpm run check 验证

        # 数据/接口上下文

        接口返回结构：
{
  "orderId": "xxx",
  "amount": 1000,  // 单位：分
  "status": 1      // 1=进行中 2=已完成 3=已取消
}

        # 四、输出格式控制

        场景 推荐格式指令
        代码生成 输出完整代码，不要省略，不要写 // ... 省略部分
        分析/Review 按严重程度分级，每条附行号和具体修改建议
        对比两个方案 用表格对比，列出优缺点和适用场景
        迁移任务 先列出迁移计划，确认后再写代码
        长任务 分步骤输出，每步完成后等待我确认再继续

        # 五、不同任务类型的提示词模板

        # 开发任务模板

        [角色] 你是一名 [技术栈] 工程师。

[任务] [动词] [具体内容]

[上下文]
- 项目：[项目名/类型]
- 相关文件：[文件路径]
- 数据结构：[粘贴关键数据]

[约束]
- 必须：[列举]
- 禁止：[列举]

[输出] 输出 [具体格式]，完成后运行 [验证命令]

        # 分析/调试模板

        [任务] 分析以下 [代码/错误/现象]，找出 [根本原因/问题]

[输入]
[粘贴代码或错误信息]

[上下文]
- 期望行为：[描述]
- 实际行为：[描述]
- 已尝试过：[列举]

[输出] 给出 [根本原因分析 + 具体修复方案]，不需要解释我已知的部分

        # 文档/Review 模板

        [角色] 你是一名有 [N] 年经验的 [领域] 工程师。

[任务] Review 以下 [代码/方案]，重点关注：
1. [检查维度1]
2. [检查维度2]
3. [检查维度3]

[输入]
[粘贴内容]

[输出] 按严重程度分级（🚫必须修复 / ⚠️建议修复 / ✅可以保留），每条附具体理由

        # 六、常见错误模式

        错误模式 问题 修复方式
        「帮我写个 xxx」 无上下文、无约束、无格式要求 补充技术栈、约束条件、期望输出
        「优化一下这段代码」 「优化」含义不明确 明确优化维度：性能/可读性/类型安全/bundle 大小
        「帮我看看有没有问题」 无检查维度 列出具体检查项
        一次提交多个不相关任务 Claude 会混淆优先级 一次一个任务，相关的放一起
        把所有背景信息堆在前面 关键指令被淹没 任务描述放前面，背景/数据放后面
