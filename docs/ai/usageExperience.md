## ai 开发使用心得

我个人和之前公司对 AI 都有一定使用，但还不是完全替代开发，人工复查 ai 的代码还需要大量的时间，更多是作为提效工具和智能化能力的补充。

从我个人角度，主要利用 AI 配合 skills 以及 claudeRules 辅助开发，分阶段使用不同的 skills，开发前的调研，需求分析，按模块开发代码，漏洞排查等，开发的时候，拿到初版代码后，我再结合项目的以及实际业务需求去进行人工校验与重构，ai 生成测试文档 交叉测试等等。

从公司角度  
我们是在尝试说全面使用 ai 禁止手写代码的方式，因为是做项目迁移，ai 有参考的代码，固定的 skills 流程，但是还是会遇到一些特殊问题 ai 处理不了的，比如说我们用的组件库是美团内部的组件库，有一些方法的使用 有的方法很类似，有的旧方法被废弃了等这些 ai 是不清楚的 还是需要人来判断使用那种方法

## 怎么把“靠人 Code Review 发现问题”，升级成“平台自动发现、自动拦截、自动修复”的工程治理能力

我觉得这件事的核心是把团队原本依赖 Code Review 的规范，转换成机器可以执行的规则。

我会先把规范拆成几类，比如代码风格、TypeScript 类型、组件使用规范、废弃 API、性能风险和安全问题。对于比较确定的规则，可以通过 ESLint、自定义规则或者 AST 静态分析去检测，比如禁止使用某个废弃组件、某个 API 必须替换成新的 API，这些都可以直接机器判断。

然后再把这些检测能力接入开发流程，比如 AI 生成代码之后自动扫描，本地提交时扫描，或者 CI 阶段扫描。发现问题以后，不只是提示错误，最好还能提供自动修复或者明确的替换建议；严重问题直接阻止合并。

对于一些没办法通过固定规则判断的问题，比如复杂业务逻辑、可维护性，可以再让 AI 做辅助检查，但是最终的硬性门禁还是尽量依赖确定性的规则。

最后把规则、扫描结果、修复建议和治理数据统一做成一个平台。这样规范就不是写在文档里靠人记，而是变成自动化治理能力，也不会完全依赖 Code Review。

## SSE AI 问答没有报错，但一直卡住，怎么排查？

我会按照 “请求 → 流 → 解析 → 渲染” 这一条链路去排查，不会一上来就只看前端代码。

如果 SSE 请求没有报错，但是页面一直卡住，我会先判断到底是后端没有返回数据，还是前端拿到了数据但没有解析或渲染出来。

第一步先看 Network，请求是不是正常建立，状态码是不是 200，响应有没有一直处于 pending。然后看 Response 里有没有持续返回数据。

如果 Response 都没有数据，那我会往后端或者网关方向排查，比如模型本身没有返回、服务端没有 flush 数据、Nginx 把流式响应缓冲了。

如果 Response 里能看到数据，那说明后端流是正常的，我就继续检查前端 ReadableStream 有没有持续读到 chunk，TextDecoder 有没有正常把 Uint8Array 转成字符串。

如果 chunk 也能拿到，我就继续检查 SSE 的解析逻辑，比如 data:、换行符、结束标识有没有处理正确，缓冲区是不是一直没有被切出来。

最后如果数据解析出来了但页面还是不更新，那就检查状态更新和 Markdown 渲染，看看是不是 React 状态没有触发更新，或者渲染层被阻塞了。

所以整体上我会从 Network、流读取、数据解析、页面渲染四层逐层缩小范围。
