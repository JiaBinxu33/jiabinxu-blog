# Spec 漂移判定标准

本指南提供漂移判定的详细标准和示例库,供执行过程中参考。

## 核心判定原则

### 文档即承诺

**只要功能在文档中被明确提及,就必须实现。未实现即为漏移。**
**仅当文档明确标注为"可选"、"待定"、"后续迭代"时,不算漏移。**

### 文档层级关系

虽然所有文档中的功能都需要实现,但修正优先级不同:

1. **DRAFT_SPEC** - 需求源头,修正时优先保持其准确性
2. **TECHNICAL_SPEC** - 技术方案,需与DRAFT保持一致
3. **feature/*.md** - 实施细节,需与TECHNICAL_SPEC对齐

## 漂移分类体系

| 类型 | 符号 | 含义 |
|------|------|------|
| 对齐 | 🟢 | 实现与规格一致 |
| 有意漂移 | 🟡 | 实现优于或合理偏离规格（有明确的改进理由） |
| 遗漏 | 🔴 | 规格要求但未实现 |
| 额外实现 | 🟠 | 规格未要求但已实现 |
| 架构偏差 | 🔵 | 实现方案与 TECHNICAL_SPEC 设计不同 |

**判定"有意漂移"的标准**：
- 代码中有注释说明为何偏离
- 偏离方向明显是更优解（如更简洁、性能更好、更符合框架惯例）
- 功能完整性未受影响

如果无法明确判定为"有意"，归类为其他更具体的类型。

## 严重度判定标准

| 级别 | 判定标准 | 
|------|---------|
| BLOCKING | **文档明确提及但未实现的功能**<br>**文档明确要求但实际不符的实现**<br>**文档未提及但实际新增的重要功能** |
| SUGGESTION |  **文档措辞不精确**<br>**文件路径/命名的微调**<br>**实现细节的合理优化(功能完整)** 

**重要**: 两个级别都需要用户确认后才能执行修正。SUGGESTION不等于"可直接修正",只是确认效率更高。

## 常见漂移模式及处理（示例）

### 模式1：文档提及但未实现(最常见的BLOCKING)

- **表现**: TECHNICAL_SPEC或feature文档中描述了某功能,代码中找不到
- **分类**: 🔴 遗漏
- **严重度**: BLOCKING
- **示例**:
  - feature文档任务12: "LX埋点集成" → 代码未集成
  - TECHNICAL_SPEC: "支持导出CSV功能" → 代码无导出按钮
  - feature文档任务5: "实现数据缓存" → 代码无缓存逻辑
- **处理**:
  - 选项A: 记录为"功能缺失-需补充代码"
  - 选项B: 更新文档,删除该功能要求
  - 必须用户确认选择

### 模式2：功能偏差
- **表现**: 文档明确要求A,实际实现了B(功能不同)
- **分类**: 🔵 架构偏差
- **严重度**: BLOCKING
- **示例**: DRAFT要求"支持2列/3列布局",实际只支持单列
- **处理**: 询问用户原因,确定是补充代码还是更新文档

### 模式3：额外重要功能
- **表现**: 实现了规格中未提及的重要功能
- **分类**: 🟠 额外实现
- **严重度**: BLOCKING(如果影响需求理解) 或 SUGGESTION(如果是次要功能)
- **示例**:
  - BLOCKING: 文档未提及用户权限,代码实现了VIP权限检查
  - SUGGESTION: 文档未提及,代码增加了加载动画
- **处理**: 询问用户是否需要补充到规格文档

### 模式4：功能完整但细节优化
- **表现**: 功能已完整实现,但实现方式更优
- **分类**: 🟡 有意漂移
- **严重度**: SUGGESTION
- **示例**:
  - 文档说用文字箭头,实际用PNG图标(视觉更好)
  - 文档说2列/3列布局,实际增加了1列居中布局
- **处理**: 更新文档,记录实际实现方式

### 模式5：文件路径调整
- **表现**: TECHNICAL_SPEC 说创建 `src/components/User.tsx`，实际是 `src/components/UserProfile.tsx`
- **分类**: 🟡 有意漂移（如果命名更合理）
- **严重度**: SUGGESTION
- **处理**: 更新 TECHNICAL_SPEC 中的文件清单

### 模式6：技术栈变更
- **表现**: TECHNICAL_SPEC 说用 Redux，实际用了 Zustand
- **分类**: 🔵 架构偏差
- **严重度**: BLOCKING（如果影响整体架构）或 SUGGESTION（如果只是实现细节）
- **处理**: 询问用户原因，更新 TECHNICAL_SPEC

## 重要约束

- **文档即承诺**: 文档中提到的功能都必须实现,不做"重要性"判断
- **证据先行**: 每一个判定必须附带实际的文件路径和代码引用
- **不做推测**: 不要推测"可能是故意不做的",如实标记为漏移
- **不改代码**: 你只负责检查和报告,不要修改任何实现代码
- **不遗漏**: 宁可多报一个SUGGESTION,也不要漏掉一个BLOCKING
- **聚焦功能**: 关注"做了什么功能"而非"代码写得好不好"
