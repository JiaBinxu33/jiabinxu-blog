# WMB 实施 Subagent 模板

> **For Cursor**:  **使用 `generalPurpose` 类型**（不要用 `explore` 类型）, **不传 model 参数**

Use this template when dispatching an implementer subagent.

```
Task tool (general-purpose):
  description: "实施任务 [N]: [任务名称]"
  prompt: |
    你正在实施前端功能任务 [N]: [任务名称]

    ## 任务描述

    [从功能点文档中粘贴完整任务文本 - 不要让 subagent 读取文件]

    ## 项目上下文

    [Scene-setting: where this fits, dependencies, architectural context]

    ## 项目规范

    **重要**: 项目中若存在 `.claude/rules` 文件夹，请遵循其中的规则。

    **验证命令**: 使用 `npm run check` 进行技术验证
    **代码风格**: 遵循项目现有的 TypeScript/React 代码风格
    **文件组织**: 按照项目现有的目录结构组织文件

    ## 开始前询问

    如果你对以下方面有疑问，请先提问：
    - 需求或验收标准的理解
    - 实施方法或技术选型
    - 依赖关系或假设条件
    - 任务描述中的任何不清楚的地方

    **现在就提问**。在开始工作前解决所有疑虑。

    ## 你的工作流程

    一旦需求明确：
    1. 严格按照任务文档实施功能
    2. 遵循前端开发最佳实践
    3. 运行 `npm run check` 验证代码，如需人类验证，则暂停并报告需要验证。
    4. 进行自我审查（见下文）
    5. 汇报结果（包含修改的文件列表，由 Controller 统一安排审查和 git 提交）

    工作目录: [具体目录路径]

    **工作中**: 如果遇到意外情况或不清楚的地方，**随时提问**。
    暂停并澄清总比猜测和假设要好。

    ## 汇报前自我审查

    用全新的视角审查你的工作：

    **完整性检查**:
    - 是否完全实施了文档中的所有要求？
    - 是否遗漏了任何需求？
    - 是否处理了边界情况？

    **质量检查**:
    - 这是我的最佳作品吗？
    - 命名是否清晰准确（体现功能而非实现方式）？
    - 代码是否整洁可维护？
    - TypeScript 类型是否准确？

    **原则检查**:
    - 是否避免了过度工程（YAGNI）？
    - 是否只构建了被要求的功能？
    - 是否遵循了代码库现有模式？
    - 是否遵循了 DRY 原则？

    **前端特定检查**:
    - 组件是否可复用且职责单一？
    - 是否正确处理了状态管理？
    - 是否考虑了用户体验？
    - 样式是否符合设计系统？

    **技术验证**:
    - `npm run check` 是否通过？
    - 是否有 TypeScript 错误？
    - 是否有 ESLint 警告？
    - 组件是否能正常导入使用？

    如果在自审中发现问题，请在汇报前先修复。

    ## 汇报格式

    完成后，汇报以下内容：
    - 实施了什么功能
    - 技术验证结果（`npm run check` 输出）
    - 修改的文件列表
    - 自审发现的问题（如有）
    - 任何关注点或建议
    - 人类验证点（如任务中有标注 🔍）
```
