# 技术方案设计

## 概述

基于明确的需求和代码仓库分析，通过协作式设计创建技术实施方案。

**Announce at start:** "我正在使用 wmb-technical-design skill 来协助你创建技术方案&实施文档，现在我要先帮你创建文档"

**Save to:** `docs/design/YYYY-MM-DD-<需求名称>/TECHNICAL_SPEC.md`

## 术语定义

| 术语 | 定义 | 对应产物 |
|------|------|---------|
| **功能点** | 产品维度的独立模块，能独立向用户交付价值 | 一个 `feature/xxx.md` 文件 |
| **任务** | 功能点内的实现步骤 | feature 文件中的"任务 1"、"任务 2"... |

**从 DRAFT.md 接收功能点时**：
- 验证每个功能点是否符合"独立交付价值"标准
- 如发现 DRAFT 中的"功能点"实际是同一模块的不同方面，应合并处理
- 合并后的功能点对应一个 feature 文件，原来的"功能点"变为该文件中的任务

## 设计流程

### 1. 创建模板文件
- 确认需求来源：询问是否有 DRAFT_SPEC.md 或其他需求文档
- **必须使用**`cp`命令复制 [TECHNICAL_SPEC_template.md](assets/TECHNICAL_SPEC_template.md) 模板**创建主文档并进行写入，严格按照文档格式填充**
- 创建文档目录结构

### 2. 代码仓库分析和初步设计
- 必须先完成第一步创建模板，才可以进行仓库分析
- **For Claude Code:** 使用find命令协助你检索，项目中若存在 `.claude/rules` 文件夹，遵循里面的规则
- **必须**使用 subAgent 探索现有代码结构和技术栈
- 分析每个功能点与现有系统的关系
- 形成功能点实施的大概思路
- 绘制整体架构图和数据流时序图

### 3. 逐个功能点协作设计

**执行约束**（必须严格遵守）：
- **禁止批量确认**：不得一次性列出多个功能点的技术决策问题
- **禁止跳过确认**：未获得用户确认前，不得进入下一个功能点
- **单点推进**：完成功能点N的全部流程后，才能开始功能点N+1

**针对每个功能点，严格按以下顺序执行**：

1. **创建子文档**：**必须使用**`cp`命令 [feature_template.md](assets/feature_template.md) 创建功能子文档

2. **代码分析**：分析现有代码，形成初步方案思路

3. **展示方案概要**：向用户展示该功能点的大致实现方案（让用户有整体把握）
   - 实现位置（在哪个文件/方法中修改）
   - 核心修改内容
   - 大致实现思路

4. **【强制停止】逐个确认技术决策**：
   - 如有需要确认的技术决策，**一次只问一个问题**
   - 发送消息后**等待用户回复**，确认后再问下一个问题
   - 决策点包括：参数定义、边界情况处理、与现有代码的关系等
   - 遵循 [quest_guide](references/quest_guide.md) 的提问格式
   - 直到所有决策点确认完毕

5. **编写文档**：用户确认后再编写文档，遵循 DRY, YAGNI 原则，文档是给下一位同事看的，他只能看懂当前的格式，改了之后系统会异常，如果某环节没有备注无即可，不要删除章节
   - 直到你有95%的信心理解某个功能点后，编写文档
   - 不要一次性完成编写，可以分段写，严格按照文档格式填充
   - **Skill 优先**：如果功能点可用现有 skill 实现，直接引用 skill 名称，不要重复编写实现细节
     - 正确：`使用 wmb-xxx skill 完成此功能点`
     - 错误：把 skill 的步骤复制/改写到文档中

6. **更新主文档**：更新主文档概要后，进入下一个功能点

### 4. 整体方案整合
- 仔细阅读所有功能点文档
- 检查功能点间的依赖关系和文件冲突
- 识别和解决潜在冲突（命名冲突、架构不一致、实施顺序依赖）
- 验证技术选型和架构模式的一致性
- 优化整体架构和实施顺序
- 最终整合提交完整技术方案

## 核心原则

- **一次一问，逐点推进**: 一次只处理一个功能点、一个问题，不要批量提问压倒用户
- **先展示后确认**: 先给出功能点的整体方案概要，让用户有全局把握，再逐个确认细节
- **Skill 优先**: 功能点能用 skill 实现就直接引用，不要重复编写 skill 已有的内容
- **精确路径**: 明确具体的文件路径和命令
- **DRY, YAGNI**: 方案保持简洁，避免重复和过度设计
- **绝对复制**: 模板创建场景**只能使用** `cp` 命令，不可直接编写
- **分步编写**：渐进式编写文档，不要一次性完成

## 交付物

**主文档**: `docs/design/YYYY-MM-DD-<功能名称>/TECHNICAL_SPEC.md`
**功能点子文档**: `docs/design/YYYY-MM-DD-<功能名称>/feature/[功能点名称].md`

## 方案完成展示

在提供执行选项前，**必须在对话中展示技术方案摘要**，让用户无需打开文件即可 review：

```markdown
## 技术方案摘要

**功能点1: [名称]**
- 实现位置: `具体文件路径`
- 核心修改: [一句话描述做什么]
- 关键决策: [技术选型/处理方式]

**功能点2: [名称]**
- 实现位置: `具体文件路径`
- 核心修改: [一句话描述]
- 关键决策: [技术选型/处理方式]

**实施顺序**: 功能点1 → 功能点2 → ...

**涉及文件汇总**:
- `path/to/file1.ts` - [修改内容]
- `path/to/file2.ts` - [修改内容]
```

用户确认方案无误后，提交技术方案文档。

## 方案提交

用户确认方案摘要后，**立即提交技术方案文档到 git**：

```bash
git add docs/design/YYYY-MM-DD-<功能名称>/
git commit -m "docs: <功能名称>技术方案设计"
```

## 执行交接

用户确认方案摘要后，询问是否开始执行：

**"技术方案已保存到 `docs/design/YYYY-MM-DD-<功能名称>/TECHNICAL_SPEC.md`。准备好开始实施了吗？"**

**如果用户确认开始：**
- **必须使用子技能:** wmb-subagent-driven-development-每个任务分派独立子代理，任务间人工审核，快速迭代
- 在当前会话继续
- 每个功能点使用独立 subagent
- 双重审查（规范符合 + 代码质量）
- 如果当前是在 **CatPaw** 的执行环境中，则要求用户确保已启用「设置-chat-任务子代理」
