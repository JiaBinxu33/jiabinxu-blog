# AI Agent

## 三种常见的 AI Agent 设计模式

这三种模式关注的是任务如何组织，没有固定的 Agent 数量要求，也不是互斥的分类，可以组合使用。

### 1. ReAct（推理 + 行动，边行动边调整）

核心：将推理与行动交替进行，根据工具或环境返回的结果，动态决定下一步行动。重点不只是“调用工具”，而是利用反馈继续推理和调整。

- **Thought（思考）**：分析当前情况，决定下一步行动，或根据上一步结果调整策略。
- **Action（行动）**：执行具体动作，例如调用搜索工具、查询数据库或运行代码。
- **Observation（观察）**：获取行动结果，例如搜索摘要、API 返回值或代码执行结果。

典型流程：`思考 → 行动 → 观察 → 再思考 → …… → 最终回答`。

例如：查询某款手机的参数 → 根据搜索结果发现版本不明确 → 补充查询具体版本 → 整理答案。

常见实现会把行动和观察结果加入上下文，也可以压缩或截断历史。循环在任务完成、达到最大步数或超时等条件下结束。

ReAct 常由单个 Agent 实现，也可以作为多 Agent 系统中某个 Agent 的执行方式。

### 2. Plan-and-Execute（规划 + 执行，先拆解再推进）

核心：先将复杂任务拆解成计划，再逐步执行；根据执行结果，必要时重新规划。

- **Planner（规划器）**：理解目标，拆解任务，确定步骤和依赖关系。
- **Executor（执行器）**：完成每个步骤，可以调用工具，也可以采用 ReAct 循环。
- **重新规划**：发现信息不足、步骤失败或目标变化时，更新后续计划。

典型流程：`制定计划 → 执行步骤 → 检查进展 → 必要时重新规划 → 完成任务`。

Planner 和 Executor 是职责划分，不代表必须有两个 Agent。可以由同一个模型分阶段承担，也可以使用不同模型或多个 Agent。

几个相关概念的区别：

| 概念                            | 侧重点                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------- |
| CoT（Chain-of-Thought，思维链） | 通过中间推理步骤求解问题；“请一步一步思考”是典型的零样本 CoT 提示            |
| Plan-and-Solve                  | 一种提示方法：先制定计划，再按计划求解，不要求独立的规划器、执行器或工具调用 |
| Plan-and-Execute                | 将规划与执行拆成独立阶段或模块，适合组织多步骤任务                           |
| ReAct                           | 推理与行动交替进行，可用于执行某个计划步骤                                   |

成本方面：使用大模型规划、小模型执行，有机会降低费用；但规划、执行和重新规划也会增加调用开销，因此不保证节省 token，费用降低也不等于 token 总量减少。

### 3. Reflection（反思，根据反馈迭代修正）

核心：生成初始结果后，根据反馈发现问题、修改结果，再次评估，争取提高输出质量。

- **生成或执行**：产出初始答案、代码或行动结果。
- **评估与反思**：检查是否满足目标，定位错误或不足。
- **改进**：根据反馈修改结果，必要时再次评估。

典型流程：`生成 → 评估与反思 → 改进 → 再次评估 → 达标或达到迭代上限后停止`。

反馈可以来自模型自评，也可以来自测试结果、工具返回值、环境反馈或人工评价。自评不保证发现错误，也不保证每次修改都让结果更好，需要明确评价标准和停止条件。

这三个环节不意味着必须有三个 Agent：可以由同一个模型多轮完成，也可以由多个 Agent 分工协作。多轮评估和修改通常会增加 token 消耗与延迟，开销取决于迭代次数和上下文长度。

相关概念：

- **Reflection**：泛指反思、检查和修正机制。
- **Self-Refine**：由同一个模型生成结果、提供反馈并迭代改进，是自反馈的一种具体方法。
- **Reflexion**：一种具体的 Agent 方法，将反馈转化为语言形式的反思经验，存入记忆，用于后续尝试；反馈可以来自外部或内部模拟。

这里的“改进”通常是通过修改输出、上下文或经验记忆来完成，不意味着自动更新模型参数。

![Reflection 流程图](/images/ai/Reflection.png)

### 三种模式如何组合

可以用一句话记忆：**ReAct 边行动边调整，Plan-and-Execute 先规划再执行，Reflection 根据反馈迭代修正。**

例如，一个编程 Agent 可以先规划开发步骤，再通过 ReAct 逐步读取文件、修改代码和运行测试，最后根据测试结果反思并修复问题。

What
检索增强生成（Retrieval-Augmented Generation，RAG）是一种结合了信息检索和文本生成的技术。它的核心思想是：在生成回答之前，先从外部知识库中检索相关信息，然后将检索到的信息作为上下文提供给大语言模型，从而生成更准确、更可靠的回答

- Retrieval ：检索
  提前查阅资料，包括内部的文档，线上资料甚至 API，最关键的是这些资料是实时的

- Augmented：增强
  先检索后生成，对于回答的答案是可以有出处的，即建议在检索的基础上

- Generation：生成
  大模型的基础内容，大模型根据我们提出的问题，按照以往训练的数据，生成答案，生成的内容是基于模型的参数，不一定能够获取数据的来源

依靠 RAG 就可以做到

- 知识有来源
- 信息有更新
- 逻辑有支撑
  的大模型问答系统

How
一个完整的 RAG 应用流程主要分为两大核心环节
数据准备阶段：系统通过数据提取、文本分割和向量化，将外部知识构建成一个可检索的数据库。
应用阶段：系统会响应用户的提问，从数据库中检索相关信息，将其注入 Prompt，并最终驱动大语言模型生成答案
数据准备阶段：文件上传阶段
应用阶段：回答阶段
